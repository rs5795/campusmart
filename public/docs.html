CampusMart – Software Engineering Documentation · ← Open the marketplace

Unit 1 · Introduction, process model & planning

Problem: Students and staff sell used books, cycles, electronics and hostel items through scattered WhatsApp groups with no search, trust or history. CampusMart gives each university its own searchable marketplace.

Process model: Incremental model (4 increments) – chosen because core features (auth, listings) are well understood, while search and messaging can be added and tested incrementally.

IncrementDeliverableWeek
1SRS, use cases, DB design, auth1–2
2Listings CRUD, image upload, details page3–4
3Search, filters, contact seller, inbox5–6
4Testing, QA, deployment, docs7–8

Risks: spam listings (mitigate: login required, validation), image abuse (type/size limits), data loss (DB backups), scope creep (payments excluded).

Unit 2 · Requirements (SRS)

Stakeholders: Buyer, Seller, Admin/Moderator, University.

IDFunctional requirement
FR1User registers/logs in with email + password; university is chosen at registration
FR2Seller creates, edits, marks sold, and deletes own listings only
FR3Seller uploads a product image (JPG/PNG/WEBP/GIF, ≤3 MB)
FR4Product details page shows price, condition, seller and university
FR5Search by keyword; filter by category and price; sort
FR6Logged-in buyer contacts seller; seller reads messages in inbox
FR7Users only see listings of their selected university
IDNon-functional requirement
NFR1 Securitybcrypt password hashes, JWT sessions, parameterised SQL, XSS escaping, upload validation
NFR2 UsabilityResponsive on mobile, tablet, desktop
NFR3 PerformanceListing search under 500 ms for 10k rows (indexed)
NFR4 MaintainabilityModular REST API, automated tests

Constraints: no online payments; free hosting; Node.js 18+.

Architecture

Three-tier client–server: Presentation (responsive HTML/CSS/JS single-page app) → Application (Express REST API: auth, validation, business rules) → Data (SQLite, relational schema with foreign keys and indexes). Justification: simple to deploy, clear separation of concerns, easy to swap SQLite for PostgreSQL.

Test levels: unit (validation rules), integration (API + DB, automated), system (manual UI walkthrough on phone and desktop), acceptance (against FR1–FR7).

Quality assurance: reliability (validation, FK constraints), security (NFR1), usability (responsive, clear errors), code review checklist.

Maintenance plan: corrective (bug tracking in GitHub issues), adaptive (move to PostgreSQL/cloud image storage), perfective (wishlists, ratings, real-time chat), preventive (dependency audits, nightly DB backup). New categories are a one-line change in server.js.
